# Decisions

## Phase 2 update

The user’s continuation brief advances imports, fresh statistics, browser distribution and a minimal desktop wrapper. Accepted current decisions are in [PHASE_2_PLAN.md](docs/PHASE_2_PLAN.md). Expo and the original content models remain; imports use CSV/XLSX with preview and explicit confirmation; recorded study replaces demo statistics; Electron reuses the web build. The following initial-stage decisions and future review rules are retained as design history, with import postponement superseded by version 0.2.

This records the starting recommendations for the Dutch learning app. The uploaded brief is product reference material. The first delivery is a working navigation shell; later features below are proposals, not completed functionality.

| Decision             | Recommendation and reason                                                                                                                                                                 | Alternatives and tradeoffs                                                                                                                                                                                              |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| First milestone      | Build Home, Levels, Vocabulary, Grammar, Review, Statistics, and Settings with a small, labelled sample dataset. Let the designer review the structure before adding learning rules.      | Building the full curriculum and backend now would make problems harder to isolate. A shell does not yet record learning or administer tests.                                                                           |
| App platform         | Use Expo, React Native, TypeScript, and Expo Router. One codebase can target Android, iOS, and web; TypeScript catches many mistakes before the app runs. Routes correspond to files.     | A web-only React app is simpler for a website but does not provide the same native foundation. Separate native apps offer more platform control but increase work. Shared code still requires testing on each platform. |
| State                | Keep screen-specific choices in React state. Use a small React context for shared local settings only.                                                                                    | Redux or another state library may help with complex shared workflows later, but adds concepts before they are needed. Avoid putting every future session and content record into one context.                          |
| Local settings       | Persist the daily vocabulary target locally with AsyncStorage. Validate saved values and recover visibly from damaged or unavailable storage.                                             | An in-memory preference disappears on restart. SQLite is better suited to a substantial local progress database, but unnecessary for one small settings object. AsyncStorage is not a secure credential store.          |
| Content and progress | Store sample educational content in dedicated files. Model learner progress separately, using stable content IDs.                                                                         | Adding personal mistake counts directly to vocabulary records would mix shared curriculum with one learner's history and hinder future accounts.                                                                        |
| Vocabulary types     | Use a TypeScript discriminated union: `wordType` determines which noun, verb, adjective, or other fields apply.                                                                           | One large object with every field optional is initially easy, but permits invalid combinations and irrelevant UI fields. A later database can keep common columns plus validated type-specific JSON.                    |
| Backend              | Defer Supabase, PostgreSQL, authentication, and cloud synchronization until local learning behavior is tested.                                                                            | A backend now would introduce account, network, privacy, and deployment issues before the learning experience exists. Local data initially stays on one device/browser.                                                 |
| Language             | Use English for interface text, instructions, and teaching explanations; Dutch appears as learning content. Keep navigation labels and reusable text easy to locate.                      | A translation framework can be added when another interface language is actually needed. No language selector is needed now.                                                                                            |
| Visual theme         | Centralize a calm nature-inspired orange, blue, ivory, and neutral palette, spacing, typography, and corner radii. Use responsive layouts and explicit text labels.                       | A large component framework can accelerate some work but constrain the desired design and increase dependencies. Reusable local components are enough for this milestone.                                               |
| Working name         | Use “Dutchly” as an editable working product name.                                                                                                                                        | Branding can change without affecting curriculum or learner data. This is not a trademark-availability claim.                                                                                                           |
| Learning evidence    | Clearly mark preview lessons, example review questions, and all invented statistics as sample/demo material. No activity is recorded merely by navigating.                                | Fictional progress presented as actual history would mislead learners. The shell is not a CEFR assessment.                                                                                                              |
| Date handling        | In the future, save timestamps in UTC and compute learning-day boundaries in a recorded IANA study timezone. See the exact proposal in the architecture document.                         | UTC calendar days alone can assign late-night study to the wrong local day. Fixed offsets do not handle daylight saving time.                                                                                           |
| Future rules         | Keep review scheduling, day completion, statistical calculations, and level estimation in independent, testable modules. The initial proposed rules are documented before implementation. | Calculations scattered through screens would be difficult to change consistently or test around midnight and repeated submissions.                                                                                      |
| Product boundaries   | Keep levels browsable. Postpone accounts, import execution, notifications, payments, AI tutoring, speech recognition, gamification, and synchronization.                                  | These can be considered individually after the core experience works; they are not required for a useful first delivery.                                                                                                |

## Unresolved choices for later milestones

- A Dutch-language subject expert should validate translations, exercises, accepted answers, and curriculum placement before the content is offered as a dependable course.
- The review policy below is a concrete starting proposal. How recurring practice works after mastery and how restored/imported progress is handled still need a product decision before implementation.
- A learner's estimated level needs validated curriculum coverage and sufficient evidence. A sample dataset cannot support that claim.
- Dataset removal will require a choice between archiving referenced content and retaining a content snapshot. Neither should silently delete unrelated progress.
- Settings are local. A future cloud account migration will need an explicit merge policy for conflicting device history.

See [architecture](docs/ARCHITECTURE.md) for entities, screen map, and future rule definitions, and [roadmap](docs/ROADMAP.md) for milestone boundaries.

# Phase 2 implementation decisions

This phase extends the existing Expo 57 / React Native app. The seven routes, word-type model, grammar-topic model, and visual theme remain in place.

1. Reopening: keep `start` and `web`; document ordinary terminals outside Codex. Keep the existing `export:web` command and add `preview:web` for the exported site.
2. Fresh activity: replace invented statistics with a separately stored, versioned activity journal. The first edition stored only settings, so there is no real history to erase. Do not clear AsyncStorage globally. Preserve settings and curriculum. Resetting activity later requires a confirmation dialog and changes only the activity key.
3. Learning evidence: an explicit “Mark studied” action records a vocabulary item once; “Complete lesson” records a grammar topic once. Merely viewing or importing records nothing. Submitted practice answers record real attempts. These actions do not claim mastery. A learning day requires five newly studied words, one completed grammar topic, or five distinct answered questions. Changing the daily target does not rewrite past days. Spaced mastery/scheduling remains a later milestone.
4. Storage: keep AsyncStorage behind a small repository, with independent keys for imported curriculum and activity. Validate saved structures, serialize writes, show failures, and block writes to damaged data. Browser/desktop tabs coordinate writes using the Web Locks API. New activity starts at zero once and persists across reopening.
5. Imports: use Papa Parse for UTF-8 CSV and ExcelJS for XLSX reading. Run browser/desktop parsing in a worker with a timeout. Limit files to 5 MiB, inflated XLSX entries to 25 MiB, and imports to 5,000 rows and 64 columns. Reject malformed containers and formulas. Native phone import is deferred; other phone screens keep working.
6. Import policy: any validation error blocks the entire commit until the source is fixed. Valid previews show duplicates as skipped; nothing is overwritten. Vocabulary duplicate key is normalized Dutch term + word type + CEFR level. Grammar checks a supplied lesson ID and normalized title + level. Import commits recheck duplicates against the latest stored content.
7. Grammar spreadsheet rows map to the existing topic object with an empty questions array. Existing questions remain unchanged. This initial import supports lesson text only; no nested JSON cells or fabricated exercises. The grammar screen handles lessons without exercises.
8. Templates: first-row field names and simple data rows, available directly from the Import screen. Headers and example rows come from the same import-schema definitions. XLSX templates use a named Vocabulary or Lessons worksheet.
9. Dataset management: list imported datasets and their counts, format, levels, dates, and status. This phase offers no dataset deletion; avoiding deletion also preserves linked learning history. Progress reset preserves every dataset.
10. Web: static Expo export in `dist` can run independently of Codex. Netlify can publish this directory with the existing build command; no deployment or paid account is created.
11. Desktop: use Electron and electron-builder, reusing the exported UI. Electron adds Chromium and a larger download, but avoids the Rust/platform toolchain required by Tauri. The renderer has no Node access, context isolation and sandboxing stay enabled, and only packaged local files are served through a private application protocol. Windows packaging is tested here; macOS signing, notarization, packaging tests, and distribution need a Mac later.

References: [Expo web publishing](https://docs.expo.dev/guides/publishing-websites/), [Electron security](https://www.electronjs.org/docs/latest/tutorial/security/), [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/), [Papa Parse](https://www.papaparse.com/docs), [ExcelJS](https://github.com/exceljs/exceljs).
